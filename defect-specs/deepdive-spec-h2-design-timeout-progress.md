The render, not the timeout, is the problem: `render_manim_infographic_mp4` in `ddma/manim_infographic_engine.py` spawns a SEPARATE Manim CLI process for EACH scene (`sys.executable -m manim -qh --format=mp4 ... <SceneClass>`), sequentially — 6 spawns for 250-1 (6 stages), each at `-qh` (high quality), each with full Manim startup overhead, for simple white-on-black line art — then concats the scene mp4s, muxes audio, and the endpoint runs `ddma.py compile-clip --source manim` as a further subprocess. The whole endpoint is synchronous (design → render → compile → return). The design thread (`_h2_run_design_group` in `ddma/beats_server.py`) waits on the curator endpoint with `urllib.request.urlopen(req, timeout=120)`, so it times out at 120s — but the curator ALSO never produces the mp4 even after 12-13 minutes, so the render itself is stalling/failing, not merely slow. Closing the browser tab does NOT kill the server thread (it is a daemon thread; the handler returns immediately and the client only polls `design_status`) — the tab is not the cause. The client-side unlock (Spec H2 XVII) is CONFIRMED working: no "Design artifacts serves episode 249 only." toast appears in any attempt, and the confirm dialog appears every time. The design directive path works; only the render step fails. SECOND GAP: the design status tracks only per-clip status (queued/running/done/failed) and done/total — "Design this clip" shows no % progress. The Mosaic button reports % progress; the Manim design does not. The progress display itself needs designing (see part (c) below) — it is not just a label to add.

Report every gap you see (render performance, the 120s timeout, background/async, progress, error handling, any other gap in this path) with: what it is, where (file + function/line), the evidence (timing or log line), and severity. This diagnosis decides what the fix in (b) covers — do not skip it and do not guess the stall point.
- **(b) Make the render fast and truly background — do NOT merely raise the timeout.** Fix the render itself, based on the diagnosis in (a): reduce the per-scene Manim spawn overhead (e.g., render all scenes in ONE Manim invocation instead of one CLI process per scene, and/or drop `-qh` to a quality that fits simple white-on-black line art), and make the endpoint truly asynchronous (the curator returns immediately with a job identifier and the design thread polls for completion, so no HTTP timeout can kill the wait). The builder determines the exact approach, but the design MUST land for 250-1 without manual intervention and without the user keeping any tab open, and the render MUST complete in a time that is reasonable on the user's Windows hardware (report the measured per-clip render time). Merely raising the 120s timeout is NOT an acceptable fix on its own — it masks the problem. Do not change the design itself (the deterministic path, the directive handling, the catalog guard) — only how the render runs and how it is waited on.
- **(c) Design how to show % progress — by measuring the process steps — then implement it.** "Design this clip" MUST report % progress like the Mosaic button does. But the progress display is not a label to bolt on — Muse Code must DESIGN it, using the measurements from (a): measure/time each step of the render pipeline (design, MP3 slice, each Manim spawn, concat, mux, compile), then design a progress mechanism based on those measurements (for example, % from steps completed out of total steps, per-scene progress, or a time-based estimate — the builder chooses the scheme that fits what the pipeline can actually report), and implement it so the Manim panel shows the % during a render. If the curator does not currently expose per-step progress, add that reporting as part of this job (it is a deliverable, not a follow-up). The `design_status` endpoint already tracks per-clip status — surface what it knows in the panel (`renderDesignStatus` in `beats.html`) and add the % field so the Design side matches the Mosaic side's % progress. Report the progress scheme you chose and why (in the build summary).
